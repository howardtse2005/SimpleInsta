# 2026-10-28

## IGScrollBlocker — "Enough" design plan

Wrote `PLAN.md` (755 lines) for an Android app that makes Instagram finite: feed only from
followed accounts, DMs normal, reels only those sent in DMs, terminal "You are all caught up".

**Research findings (prior art):**
- `brosssh/morphe-patches` (~350★) — ReVanced/Morphe APK patches, already has "Disable Reels
  scrolling" + "Limit feed to following profiles". Pinned to IG 439.0.0.37.89, needs signature
  bypass → breaks Play Integrity.
- `ReSo7200/InstaEclipse` (~1.6k★) — Xposed module (Vector/LSPosed + LSPatch). Uses DexKit to
  resolve obfuscated methods structurally, so it survives IG updates. Has "Lock Reels scrolling"
  and "Following only feed". Needs root or LSPatch repackaging.
- `AlexMatter1512/justagram` (~68★) — Capacitor WebView wrapper, per-surface CSS rules incl.
  `dmOnlyMode.css`. Hide-only, no finite model.
- `matom664/InstaDm` — Kotlin/Compose WebView wrapper, blocks `/reels` at URL layer + DOM
  reinforcement. Best reference architecture; explicitly no private API / no cookie extraction.
- Barinsta (dead 2021) — cautionary tale for private-API clients.

**Decision:** WebView shell (~3MB) + document-start injected policy engine. Core insight: don't
block gestures, remove the data source — rewrite `page_info.has_next_page` so Relay's `loadNext()`
no-ops and IG renders its own end-of-feed state. Native `shouldInterceptRequest` as enforcement
tier. DM-sent reels extracted from thread JSON into a native Media3 playlist with Prev/Next buttons
(no vertical swipe) → literal finite queue.

**Key design rules captured in Appendix A:** structural matching only (no doc_id / hashed class
names), JS decides + Kotlin enforces, delete routes don't hide buttons, degradation ladder
FULL→FEED_ONLY→HIDE_ONLY→SAFE, app never stores media.

**Open risk:** M0 spike must prove WebView login + feed pagination rewrite + DM reel JSON before
any UI work. Google/Facebook OAuth will not work in WebView (`disallowed_useragent`); username +
2FA only.

Working title: `Enough`, package `app.enough.ig`.

## First real device bug: ERR_UNKNOWN_URL_SCHEME

User hit: `intent://instagram.com/_n/mainfeed?...` → `net::ERR_UNKNOWN_URL_SCHEME`.

**Root cause:** `UrlPolicy.isInstagram()` matched on *host* only. An `intent://` URL has host
`instagram.com`, so it passed the "is this Instagram?" check, `isBlocked("/_n/mainfeed")` was false,
`shouldOverrideUrlLoading` returned false, and the WebView tried to load the intent. Host is not the
question; **scheme** is. Instagram's web app fires this to hand off to the native app — i.e. the exact
bypass the product exists to prevent.

**Fix (three layers):**
1. New `web/UrlGate.kt` — pure string scheme parsing (RFC 3986), no Android types so it is unit
   testable. `isWeb` = http/https only; `isAppHandoff` = intent/instagram/fb/market/whatsapp;
   `isExternalApp` = mailto/tel/sms. `WebHost` refuses every non-web navigation and never launches IG.
2. `00_runtime.js` app-handoff firewall — capture-phase click handler + `window.open` patch, so the
   intent never reaches the browser at all.
3. `onReceivedError` safety net — if a non-web main-frame nav slips through, restore `lastGoodUrl`
   (debounced 4 s so a retrying page can't loop).
4. `/_n` added to `BLOCKED_PREFIXES`; `UrlPolicy.labelFor()` gives friendly chip text.
5. Re-tapping the active tab reloads its root — escape hatch for a dead overlay left behind.

**Tests:** 16 Kotlin (10 watermark + 6 UrlGate), 17 policy (4 new handoff cases). Release 1.65 MB,
bundle 21 KB. New APK in `dist/`.

**Lesson:** URL gating must be scheme-first. A host allowlist will happily admit `intent://`,
`javascript:`, and `data:` if you only check the authority.

## Round 3: the real root cause (from a screenshot)

User sent the debug sheet: `policy: attached` · `feed: no feed response yet` · `watermark none` ·
`HIDE_ONLY`.

**Root cause:** Instagram's web app issues same-origin requests as **relative** URLs
(`fetch('/graphql/query')`). `E.isInstagramUrl()` required the string to contain `instagram.com`, so
`shouldInspect()` returned false for *every* request. The policy was attached and running, but
completely blind: no feed filtering, no pagination cap, no DM reel extraction, empty queue. That is
why the reel pager kept working — nothing was ever intercepted, and there was nothing in the queue to
send them to.

Fix: `E.resolve(url)` resolves against `location.href` before any classification; fetch and XHR
wrappers resolve at capture time. Regression test added — the Node sandbox was *also* missing `URL`,
which is why the harness had never caught it.

**Also:**
- Long-press on "Enough" appeared to open Instagram because the debug dialog's first button was
  "Open Instagram" (and it was enabled even with `allowAppHandoff` off). Removed that button; the
  hold-to-open chip is the only door now.
- Added a URL-level reel guard: patch `history.pushState` + a 500 ms `setInterval` watching
  `location.pathname` for `/reel/`. On detection → `openReel` + `replaceState(lastSafe)` + `popstate`
  so the pager unmounts. This does not depend on the bubble being an anchor.
- Added `E.logEvent` → native ring buffer (60 lines) shown in the debug sheet as "What the page saw".
  Logs: taps in DMs (with href or "not an anchor"), reel links, reel URLs, feed pages.
- Warning strip now also shows when `feedSeen == false`, not just when the policy is missing.

**Tests:** 25 policy, 16 Kotlin. Release 1.69 MB, bundle 31 KB.

**Lesson:** instrument before fixing. Two rounds of DOM-level guessing were wasted because the app
could not report whether it was even looking at the right responses. The one-line
`feed: no feed response yet` was worth more than all the synthetic tests.
**Second lesson:** a sandbox missing a global (`URL`) can hide exactly the bug you are hunting.

## Round 4: empty payload read as "end of feed"

Screenshot after the URL fix: `feed: kept 0 · removed 0 · pages 0 · ended`, `watermark 1793202931`,
`FULL`, and the page behind was Instagram's **logged-out landing page**.

**Bugs:**
1. `!hasPosts && !anyHasNext` → `reason = 'exhausted'` fired on any payload without posts, including
   the landing page. That posted caughtUp and ran `Watermark.advance(EXHAUSTED)` → watermark = now.
   Consequence: after signing in, every post looks older than the watermark, so the feed ends after
   one page. The bug quietly bricked the feature it was meant to implement.
2. The red "Limits aren't running" strip fired on `feedSeen == false`, which is also true when the
   user is simply logged out → false alarm.

**Fixes:**
- `E.hasFeedShape(json)` gates only the *end-of-feed* logic (payload must contain a `page_info`
  connection). Cleaning still runs on everything — gating both broke suggested-module stripping, and
  a test caught that.
- Exhaustion now also requires `E.state.feedSeen` (posts seen earlier in the document).
- `Watermark.advance` clamps `current > now + 60` to 0 (future = corruption). Test updated: the old
  "never moves backwards" case used a future value, which the clamp now correctly rejects.
- `Prefs.migrateIfNeeded()` + `limits_version = 2` clears watermarks written by older builds, so an
  existing install self-heals on upgrade.
- Health now reports `payloads` + `loggedOut`; native degrades only when `payloads > 0 && !feedSeen`.
  Logged-out shows a "Sign in to Instagram" chip instead.
- Debug dialog: "Reset feed limits" button; "Open Instagram" button removed (it was the accidental
  exit path behind the long-press confusion).

**Tests:** 28 policy, 18 Kotlin. Release 1.70 MB, bundle 33 KB.

**Lesson:** a "no data" payload must never be interpreted as "no more data". Absence of evidence was
treated as evidence of absence, and it silently wrote state (the watermark) that broke the feature
long after the bad read.
**Meta-lesson:** the debug sheet found three distinct bugs in three rounds. Instrumentation beat
synthetic tests every time.

## Round 5: the reel is not a link

Screenshot: Messages tab, full-screen reel playing, log line **`tap: (not an anchor)`**.

**Conclusion:** the DM reel bubble is not an `<a>`, and the viewer is a full-screen overlay that does
not change the URL. Both prior defences (click firewall on anchors, router guard on `/reel/`) were
structurally incapable of catching it. No amount of selector tuning would have fixed this.

**New approach — stop detecting the tap, detect the result.** A video whose `getBoundingClientRect`
covers ≥90% width and ≥55% height inside `/direct` is a reel pager. Lay a transparent,
`touch-action:none` fixed div over it (`#enough-shield`, z-index max) that swallows touchstart /
touchmove / wheel. Swipes never reach Instagram. Exits: "Open in Queue" (posts `openReel` with empty
shortcode → native switches to Queue, WebView hidden) and "Done" (clicks IG's `[aria-label="Close"]`,
falls back to `history.back()`, never just removes the shield and leaves scrolling enabled).

This is the only guarantee in the app that does not depend on Instagram's markup — it depends on the
video being big, which is the definition of the thing being stopped. Trade-off documented: the viewer
is non-interactive while shielded.

**Also:**
- `openReel` with an empty shortcode is now valid (shield cannot always name the reel).
- Health failures now only count on the feed route — `HIDE_ONLY` had persisted because the Messages
  tab was being judged for not having a feed.
- `LIMITS_VERSION = 3` so the stored degradation clears on upgrade.
- `E.hasDirectShape()` gates `processDirect` cheaply; DM payloads can arrive via `/api/graphql` with
  no "direct" in the URL, so URL substring matching was never sufficient.

**Tests:** 28 policy, 18 Kotlin. Release 1.70 MB.

**Lesson:** when three rounds of interception fail, the assumption is wrong, not the selectors. The
reel was never a link. Detect the artefact (a full-screen video), not the gesture that produced it.

## Round 7: I added a second nav bar (my mistake) + shield was too blunt

User screenshot showed **two rows** of icons: Instagram's own nav inside the page, plus my Compose
bar underneath. I had added a bar instead of fixing the one already there.

**Fixes:**
- **Deleted the Compose `BottomBar` entirely.** Navigation is now Instagram's own. `tab` is derived
  from `onPath` (`/direct*` → MESSAGES, else FEED) instead of from buttons; the tab→`loadUrl` effect
  became a single initial load. Queue gets a floating "N reels waiting" pill, shown only when
  non-empty, because IG's bar cannot reach it.
- **Plane off-centre:** hiding the Explore/Reels *anchors* left their wrapper divs occupying flex
  slots. `collapseNavGaps()` in `30_dom.js` hides a wrapper only when it contains no other visible
  link (safer than `div:has(> a[…])`, which can match the nav itself). Re-runs every 1.5 s because
  React re-renders the nav.
- **Dark mode:** system now wins (`isSystemInDarkTheme() || reported == true`). Added
  `values-night/themes.xml` + `enough_bg_dark`, and themed the WebView background from
  `uiMode`, so no white flash.
- **Removed the "Limits aren't running" strip** — it had done its diagnostic job and was firing on the
  wrong tab.
- **Replaced the touch-eating shield with a drag-only freeze.** The overlay stopped scrolling by
  killing all interaction, which removed like/comment/share/save/follow/tap-to-pause. Now
  `touchmove` is cancelled (taps never fire `touchmove`, so every control works) and the pager's
  scroller is pinned to `overflow-y: hidden`. This is the better trade: block the gesture, not the
  user.
- **Proportion:** `object-fit: cover` had no effect because the *container* was narrower than the
  screen, not the video. `fillViewport()` grows up to 3 ancestors to viewport size before cover is
  applied.

**Verified:** 18 Kotlin tests, 28 policy tests, release 1.70 MB, `values-night` resources present in
the APK, `enough-shield` absent from the packaged JS.

**Lesson:** when a platform already renders the chrome, adding your own is duplication, not a feature.
Fix the existing one.
**Lesson:** a full-screen blocker is the bluntest possible instrument. Cancel the gesture you object
to (`touchmove`), not the whole input surface.

## Round 8: fillViewport broke the overlay; comment sheet couldn't scroll

User: right-side like/comment rail half cropped, comments can't scroll past the fold, likes/reposts
show but don't register, save missing, plane still off-centre.

**Cause of the crop (my regression):** `fillViewport()` set ancestors to `width: innerWidth px`. Any
left offset on those ancestors pushed content right, so the engagement rail went off-screen. Removed
entirely. `fitVideo` now applies `transform: scale(max(vw/w, vh/h))` with `transform-origin: center`
and sets the parent `overflow: visible`. Visual only — no layout surgery on someone else's DOM.

**Comment scrolling:** the blanket `touchmove` block also killed every panel. Added `scrollableFrom()`
— if the touched node has a scrollable ancestor that is not the frozen pager, the drag is allowed.
Comments and the share sheet scroll; the pager does not.

**Likes not registering:** cannot reproduce. Two actions: (a) a mutation guard — any fetch whose body
matches `/mutation/i` is returned untouched, so we can never rewrite a like/save/follow response;
(b) every mutation is logged as `mutation <status> <url>` in the debug sheet, so the next report has
evidence instead of a guess. Added a regression test asserting the response is byte-identical.

**Nav centring:** `collapseNavGaps` was too timid (one empty slot survived). Replaced with
`layoutNav()`: find the lowest `a[href="/"]`, walk up to the container holding ≥3 anchors, hide every
child with no usable link, then force `display:flex; justify-content:space-evenly`. Arithmetic instead
of guessing at Instagram's flex rules.

**Honest limits:** the DM reel viewer is a reduced UI. Save may simply not exist there, and
hold-to-speed is native-app-only. Full engagement parity would require routing DM reels to the
canonical `/reel/<code>/` page — currently blocked by `UrlPolicy` — with the freeze keeping it
single-reel. Offered to the user; not done unilaterally because it risks the scroll fix.

**Tests:** 29 policy, 18 Kotlin. Release 1.70 MB. `fillViewport` confirmed absent from the APK.

## Round 9: transform was the crop; perf work

User: rail still half cropped, cannot post, app laggy.

**The crop was mine again.** Round 8 replaced `fillViewport` with
`transform: scale(max(vw/w, vh/h))` + parent `overflow: visible`. That zoomed the video and widened
the document, pushing the engagement rail off the right edge — the same symptom, a different cause.
Removed entirely. `fitVideo` now only sets `object-fit/width/height` once per element (guarded by
`data-enough-fit`) and unmutes. **Conclusion: Instagram's web viewer frames the video itself; every
attempt to force edge-to-edge has cost the overlay. Not worth it — stop trying.**

**Performance.** Four fixes, all self-inflicted:
1. Responses are pre-filtered on raw text (`"page_info"` / `"item_type"`) before `JSON.parse` — most
   responses on the page are irrelevant, and we were parsing, walking and re-serialising all of them.
2. `fitVideo` no longer calls `getBoundingClientRect` (was running on a 400 ms timer = layout thrash).
3. `scrollableFrom` memoised per touch target — a drag fires dozens of touchmove events against the
   same node, each previously walking `getComputedStyle`.
4. Timer intervals relaxed: freeze 400→900 ms, URL guard 500→1000 ms, nav layout 1200→4000 ms
   (and it now applies once via `data-enough-nav`), theme unchanged.

**Posting.** Not blocked by us: `/create/` is allowed, and the "+" in the top bar is untouched.
Instagram's mobile web build is the likely limit — post/story creation is desktop-web/native only. If
tapping "+" produces our "The Instagram app isn't available" chip, the handoff is being refused and
the hold-to-open door is the honest path. Asked the user what they actually see.

**UI parity.** A wrapper renders Instagram's web app; it will look like IG web, not the native app.
The chrome (dark mode, single nav) now matches; the page itself cannot.

## Round 10: the crop was never the video; posting was a missing callback

User: rail still cropped, still cannot post, back needs two presses.

**Crop — third and final diagnosis.** With no transform of mine left, the rail was *still* cut. So the
cause was never the video: the reel viewer sizes its container by **height**, so a 9:16 video computes
a width wider than the screen; that widens the document and pushes anything anchored right (the
like/comment rail) off the edge. Fix is overflow clamping, not geometry:
`html, body { overflow-x: hidden; max-width: 100% }` + `video { max-width: 100vw }`.
**Stop attempting edge-to-edge.** Two attempts (innerWidth ancestors, scale transform) each cost the
overlay. Instagram's framing stays.

**Posting — not a route rule at all.** The real blocker: `WebHost` had no `onShowFileChooser`, so when
IG's create flow asked for an image the WebView silently did nothing. (A parallel change added the
hook to `WebHost.Hooks`; the build then failed with "No value passed for parameter 'onFileChooser'" and
that error is what surfaced it.) Wired `rememberLauncherForActivityResult` +
`ActivityResultContracts.StartActivityForResult` in `AppRoot`, forwarding the chosen URI back through
`ValueCallback`. Also narrowed the `/_n/` block to `/_n/mainfeed` only — blocking the whole namespace
could swallow ordinary web routes — and made `layoutNav` never hide a child containing
`button / [role=button] / input / [contenteditable]`, since Create is a button and hiding it is
indistinguishable from "posting is broken".

**Back button.** Page now posts `reelOverlay {open}`; `BackHandler` calls
`window.__ENOUGH_CLOSE__()` (clicks IG's Close/Back control, falls back to `history.back()`) before
falling through to history navigation. Previously the press went straight to `goBack()`, which did
nothing visible, hence two taps.

**Tests:** 29 policy, 18 Kotlin. Build must be verified — Kotlin signature changes broke it once.

**Lesson:** when a UI symptom survives three different fixes, the model of the cause is wrong. The
rail was never the video's width; it was the document's. Measure the container, not the content.
**Lesson:** "cannot post" in a WebView is usually `onShowFileChooser`. Silent by default.

## Round 11: discard dialog, back traps, rail clamp, nav timing

User: "Discard Photo?" doesn't leave the page; rail still cropped; nav off-centre on first load;
back needs two presses; trapped on the messages page.

**Discard — two causes, both ours:**
1. `onReceivedError` treated *any* failed non-web navigation as an app handoff and reloaded

   `UrlGate.isAppHandoff()` triggers recovery.
2. `shouldOverrideUrlLoading` swallowed every non-web scheme, including `about:` and `blob:` — which

**Back traps:**
- `tab == Tab.MESSAGES` branch only flipped a variable without navigating → first press did nothing,
  second fell through. Removed.
- New rule: queue → close queue; reel overlay → close reel; at feed root → `finish()`; else `goBack()`;
  else load HOME. The `atHome → finish()` clause is what stops "walking Instagram's history forever".

**Rail (attempt #4):** `overflow-x: hidden` stopped the page scrolling but still clipped, because the
container itself is wider than the viewport (sized by height for 9:16). Now the video's parent chain
gets `max-width: 100vw` — a maximum, not a fixed width, so nothing else moves. Explicit widths broke
the overlay twice; this is the least invasive remaining option.

**Nav timing:** `layoutNav` only ran on a 4 s interval, so first paint was Instagram's own layout. Now
runs at 150/400/900/1600/2600/4000 ms then settles to the 4 s watch.

**Tests:** 19 Kotlin (added `isTeardownScheme` case), 29 policy. Release 1.71 MB. Verified new policy
strings are inside the APK.

**Lesson:** a wrapper's own "helpful" recovery logic can undo a user action. Error handlers must be
narrow — chasing every failed navigation is indistinguishable from refusing to navigate.

## Round 12: the debug sheet settled it

Screenshot showed `feed: payloads 4 · kept 0 · pages 0` and
`feed.shape: data,extensions > get_slide_mailbox_for_iris_subscription`.

**False positive:** `hasFeedShape` accepted any object with `page_info`; Instagram's DM mailbox

**Lesson:** when a UI symptom survives five fixes, stop fixing and start measuring. The `reel.geom`

**Video width == viewport width.** There is no letterboxing left on our side; the remaining 69 px is
Instagram's reply bar. So "resolution still broken" is not a bug I can fix — it is the `cover` vs
`contain` trade-off, and both have been requested at different times. Turned it into a setting:
`Prefs.reelFitFill` → `cfg.reelFit` → `object-fit`, toggled in the debug sheet (reloads the page,

**"You're all caught up"** now renders only when `tab == FEED && !reelOpen`. Over a DM reply bar it
looked like a stray toast.

**Performance — the real find:** the non-passive `touchmove` listener was registered on `document`
for the entire session. That forces the compositor to wait for the handler on *every* scroll even
when it returns immediately. It now attaches on freeze start and detaches on thaw, so normal

**`LIMITS_VERSION` → 4** clears the `HIDE_ONLY` left by the DM-mailbox false positive.

**Tests:** 19 Kotlin, 29 policy. Release 1.71 MB.

**Lesson:** a listener that does nothing still costs something. `passive: false` on `document` is a
global scroll tax — scope it to the state that needs it.

## Round 14: the rail was a box-model bug

Screenshot: video full-bleed, rail still clipped ~half an icon.

**Cause (finally):** `box-sizing`. The frame was forced to `width: 100vw` while still `content-box`,
so its *total* width was `100vw + padding`. Everything anchored to that right edge sat exactly
`padding` past the screen — the "half an icon" symptom precisely. Fix: set `box-sizing: border-box`
and zero the horizontal padding **before** applying the width. Also clamped `#react-root` etc. to
`100vw`, because the rail is `right: 0` of whatever containing block Instagram picked.

**The measurement was incomplete, not wrong.** `reel.geom` reported sizes only (390x645 vs 390x714),
which cannot distinguish "video too small" from "overlay shifted right". It now logs
`@left`, `inner`, `client`, `scroll` — offsets and viewport widths are what actually diagnose clipping.

**Also:** the working tree reverted my `width: 100vw` widening and the geom log between rounds (a
parallel edit). Had to re-read and re-apply against current content. **Always grep before editing
this repo's policy files.**

**Tests:** 19 Kotlin, 29 policy. Release 1.71 MB.

**Lesson:** when an overlay is clipped but the media looks right, suspect `box-sizing`, not the media.
Sizes describe the element; the box model decides where its edges actually land.

## Round 16: the rail margin was a padding I deleted

## Round 17: the rail's *container* was 503 px wide

```
reel.overflow: 16..711 16..519
```

`16..519` = a box **503 px wide at x=16** inside a 390 px viewport, i.e. 129 px past the screen. The
reel viewer sizes its overlay by the video's aspect ratio at full height; a ~4:5 reel at 645 px tall
computes 503 px wide. The rail was never mispositioned — it was anchored to a box wider than the
phone.

`reel.overflow` now clamps as well as reports: elements whose right edge passes `innerWidth` by ≤200 px
get `max-width = innerWidth - left` once, with `border-box`, flagged `data-enough-clamped`. The
695 px carousel (`16..711`) is deliberately excluded — it lives in its own horizontal scroller and
squashing it would break that scroller instead.

**Why this took seven rounds:** each measurement I took (width, offset, scrollWidth, scale) described
the *video*, and the video was always correct. The broken element was a sibling box that no video
measurement could reveal. `reel.overflow` — scanning every element's right edge — is what finally
named it.

**Tests:** 19 Kotlin, 29 policy. Release 1.71 MB. Clamp code confirmed in the packaged JS.

**Lesson:** when the thing you're measuring looks perfect and the screen disagrees, you're measuring
the wrong element. Enumerate the neighbours, not the subject.

## Round 21: my two fixes were fighting each other

```
video 390x645@51   overflow: 51..441
reel.rail: inset 25
```

Both symptoms were self-inflicted:

1. **The black band was `width: 100vw`.** Instagram centres the reel frame; forcing a full-viewport
   width on a centred box moved it to x=51 and pushed it 51 px past the right edge. `max-width` can
   only shrink, never reposition — it is now the only lever used on the frame.
2. **The rail nudge matched 25 elements.** `inset 25` = twenty-five boxes translated 12 px left,
   shifting the layout it was meant to repair. Removed entirely.

**Replacement technique:** fill the frame's padding box instead of deleting the padding —
`width: calc(100% + padLeft + padRight)` with `margin-left: -padLeft`. The padding stays (it is the
rail's margin); the video extends underneath it. Nothing is repositioned.

**Tests:** 19 Kotlin, 30 policy. Release 1.71 MB. Verified 0 `data-enough-rail` in the APK.

**Lesson:** two independent "fixes" in the same layout are not additive — the rail nudge and the width
forcing were each compensating for the other's damage, which is why toggling fit modes appeared to
"fix" the icons. When a heuristic matches 25 elements it is not a heuristic, it is a blunt instrument;
and when a fix needs a second fix to look correct, the first one is wrong.

## Round 23: the feed regression was mine — the user named it

## Round 25: the app was poking the page while idle

Idle "Something went wrong" + intermittent strangers after reload.

Two loops were still mutating Instagram-owned nodes for the life of the page:
- `ensureViewport` rewrote `<meta name="viewport">` every 5 s. If IG rewrote it back, they fought in a
  loop, forcing re-layout each round. Removed entirely — added for the reel layout, never helped.
- `layoutNav` re-applied `display:none` to nav children every 6 s. Continuous mutation of React-owned
  nodes is exactly what trips an error boundary while nothing happens. Now runs a few passes after
  load and stops.

**Cursor fail-safe:** if survivors carry no usable cursor, sending the old one names a deleted post —
which is what the idle prefetch was doing. Pagination is now closed in that case. Test added
(`closes pagination when it cannot repair the cursor`).

**Still open:** strangers after reload, intermittent. `feed.markers` / `feed.keys` are the next data.

**Tests:** 19 Kotlin, 33 policy. Release 1.71 MB.

**Lesson:** a timer that mutates the DOM is a standing invitation to a race. If a correction is needed
once, apply it once — a permanent loop is not a safety net, it is an ongoing conflict with whoever
else owns that DOM.

## Round 26: back was eaten by a stale boolean

Back from Messages → Feed stopped working. Two faults:
